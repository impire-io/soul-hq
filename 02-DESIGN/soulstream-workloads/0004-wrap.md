# 0004 — Wrap: an agent answers mentions where you run it

*Graduated from research `agent-participation` (episode
[0082](../../04-JOURNEY/0082-ecosystem-agent-participation.md)); first built
as the central "waker" daemon (M3.2, episode
[0083](../../04-JOURNEY/0083-workloads-the-waker-lands.md),
[`specs/005-the-waker/`](../../../soulstream-workloads/specs/005-the-waker/)),
then **reshaped at the operator's direction**: the byname "waker" retired
for the plain word **wrap**, and the central daemon **cut** in favor of the
personal wrapper (episode 0085). Everything the research and the first
build measured carries forward; the measured corrections are marked.
Status tags: **[V]** unless marked.*

Wrap is how an agent answers mentions: **you run your assistant's wrapper
on the machine where that assistant already lives** — your logins, your
config, your models — and mentions of its persona reach it as invocations.
`soulstream wrap` is the whole act: the core CLI resolves your identity
and hands off to the `soulstream-wrap` binary (the external-subcommand
seam, §8), which holds the agent's credential and runs one harness turn
per wake. Nothing here adds wire vocabulary: the wrapper is a subscriber
and a client of the record, never a second control plane.

## 1. Vocabulary

- **Wrap / the wrapper** — one process, one agent, one credential: the
  personal runtime that turns mentions into harness invocations.
- **Wake** — one mention of the wrapped persona, ending in exactly one of:
  an outcome op in the topic (answered), or nothing yet (pending — the
  record shows no outcome, so a later wrapper run answers it).
- **Invocation template** — the per-harness configuration that keeps the
  wrapper harness-agnostic: command argv plus terminal-event mapping (§5).
- **Outcome op** — the one `turn.post` a wake leaves behind: the reply, or
  the agent's own report that it could not answer.

## 2. Standing **[V]**

The wrapper holds **only the agent's own credential** — the copy-paste
block episode 0079 mints (URL + sentinel + `sit_` token) or an equivalent
creds file. Measured basis: the agent's scope already allows subscribing
its own notify subject and reading/writing the topics it participates in;
what it cannot do — create durable consumers, mint, act as anyone else —
the wrapper deliberately does not need (§3). No operator credentials, no
support-layer standing, no second persona. Revocation semantics carry
over unchanged from the research: take the credential away and the next
connection is refused (~2ms, server-enforced); the persona stays
mentionable and its history attributed; re-grant re-admits.

## 3. Position is the record, not a consumer **[V mechanics / D as one process]**

The first build held a durable JetStream consumer per agent — the very
requirement that forced operator standing. The wrapper drops it: because
every outcome publishes under the **deterministic wake op-id** (§6), *the
record itself is the position*.

- **Catch-up, on start**: read the persona's inbox (the notify stream's
  bounded newest-100 window — protocol, `realm.InboxWindow`); for each
  mention, derive the wake op-id and materialise the topic — an existing
  outcome op means answered, skip; absent means pending, wake now.
- **Live**: a raw subscription on `SOULSTREAM.PERSONA.NOTIFY.<persona>`
  (in scope for the agent). Each arrival runs the same
  outcome-existence check before invoking, so restart races and
  duplicate deliveries collapse to no-ops.
- **Retry** is the wrapper's own in-process budget per wake; a crash
  loses nothing — the next start's catch-up finds every pending mention
  still inside the window. The window is the honest bound, stated, not
  hidden: mentions older than the newest 100 fall away (notifications
  are pointers; the mentioning ops stay in topic history forever).

## 4. The wake protocol **[V]**

Per wake (mention of the wrapped persona, not authored by it — the
self-mention guard is measured and stays):

1. **Outcome-existence check**: materialise the topic; the wake op-id
   already present means answered — stop.
2. **Materialize context**: before-snapshot of contributions, anchoring
   op's author and body into the prompt.
3. **Invoke** the harness per template: fresh run dir under scratch,
   generated MCP config bound to the agent's credential, environment
   scrubbed of inherited `SOULSTREAM_*`, stdin closed, process-group
   kill at the run budget. The event stream decides — never the exit
   code, never prose.
4. **Discharge** (§6).

## 5. The invocation template **[V]**

Unchanged from the first build, including the measured corrections:
command argv with `{{PROMPT}}`, `{{TOPIC}}`, `{{MCP_CONFIG}}`,
`{{RUN_DIR}}` placeholders; prompt template with `{{PERSONA}}`,
`{{TOPIC}}`, `{{AUTHOR}}`, `{{OP_ID}}`, `{{BODY}}`; a required
machine-readable terminal mapping (dot-path type field, terminal value,
text field, optional status/success) — a harness without one is refused;
an optional `env` block for the harness's own provider credential
(`ANTHROPIC_API_KEY`, …) when the host's login state isn't the lane
**[D — the per-agent env block is designed here, built with the
wrapper]**. Harness idioms live in templates, never in wrapper code —
measured: two structurally different grammars ran through a
byte-identical engine on template-only changes. The wrapper ships named
presets (claude-code, codex) so `soulstream wrap --harness claude` needs
no template authoring for the common cases **[D]**.

## 6. The reply obligation **[V]**

The wrapper owns the reply; the MCP tools remain enrichment (measured:
with the posting tool removed, the reply still lands). Every outcome
publishes under the wake's one deterministic op id — **UUIDv5 of the
notify op id and the agent persona** (one mention can tap several
agents; a wake is one delivery to one agent — the collision was measured
in the first build's gate) — via core's idempotent turn post, so reposts
dedupe inside the record's window and the outcome-existence check covers
every longer distance. Correlation of mid-run self-posts stays the
**before/after snapshot difference** (never stream-order anchoring — the
measured trap). A harness that posts its own reply carries its own
idempotency: the wrapper's guarantee covers the wrapper's posts — named,
not hidden.

## 7. Authorship **[V mechanics / amended for one persona]**

Everything the wrapper posts is authored by the agent, mechanically —
core stamps the author from the client's persona, and the wrapper holds
one client. The reply is the harness's terminal text. *Failure is
self-report*: "I was asked and could not answer: … " in the agent's own
voice — legitimate where the first build's ghostwriting was not, because
it is the same principal that would have replied, not a second party
speaking as the agent. The two measured loop guards stand: a failure
report **taps only the asker** (tapping yourself is absurd; tapping the
agent was the measured runaway), and a mention **authored by the wrapped
persona itself never wakes it**. A revoked agent still cannot speak at
all — its silence plus the pending mention in the record *is* the
signal, and the wrapper's log says why.

## 8. The command seam: `soulstream wrap` **[D]**

The core CLI grows **external subcommand dispatch** (the git pattern): an
unrecognized verb `X` execs `soulstream-X` from PATH, passing the
resolved identity down as the environment contract that already exists
(`SOULSTREAM_CONTEXT/REALM/PERSONA/URL/CREDS/TOKEN`, resolved once by
the CLI's own precedence rules). No plugin registry, no RPC: any
`soulstream-*` binary is a verb, and `soulstream-wrap` (shipped from
soulstream-workloads, which owns the engine) is the seam's named first
occupant. Constitution S2 holds: the dispatch is ~a screen of code, and
the seam exists because its occupant does.

## 9. The central daemon — cut, with its reversal condition **[measured basis]**

The first build's multi-agent daemon (`waker serve`: durable consumers,
operator standing, third-person failure testimony) is **cut** at the
operator's direction: personal wrap is the consumer-proven need, and the
daemon's extra machinery — the consumer rights no agent scope grants,
the support-layer credential, the second persona — existed only to serve
a deployment shape nothing deploys yet. The engine it proved survives
inside the wrap package; the specs/005 artifacts stay frozen as the
record of what was built and measured. **Reversal condition**: a realm
operating agents as infrastructure — nobody's laptop, centrally
credentialed (observable: an operator running several wrappers under a
process supervisor and asking for one process, or the fleet's claim
path landing) — brings the serve arm back as a fleet-era feature over
the same engine, with design 0003's placement answering which node runs
a wake.

## 10. Open, named **[O]**

- **Loop safety**: unchanged — two measured exhibits now (the research's
  reply-mention notify and the first build's failure-turn runaway). The
  wrapper is still the budget point; agent-wakes-agent budgets remain a
  successor research topic before any such deployment.
- **Harness-as-workload**: running wraps behind the backend seam
  (isolation, artifacts, provider-key delivery through the per-workload
  secret channel) keeps its named trigger — a registration pointing at
  an artifact rather than a host command — and its provider-key custody
  question stays tied to the tenancy topic's D9 (the custodian storing
  third-party secrets).
- **Shell surfacing**: the credential screen's set-up folds grow the
  wrap one-liner; registrations-as-shell-objects stay a product
  composition question.

## 11. Acceptance criteria

1. On a machine with a logged-in assistant and the agent's credential
   block, `soulstream wrap` (or `soulstream-wrap` directly) answers a
   mention posted while the wrapper was **not** running: exactly one
   reply turn authored by the agent, under the deterministic wake op-id.
2. Kill and hang faults end in exactly one agent-authored self-report at
   the retry budget; a mid-run MCP self-post is never duplicated;
   restarting the wrapper answers nothing twice.
3. With the credential revoked, the wrapper refuses loudly and posts
   nothing; the persona stays mentionable; re-grant plus a restart
   answers the pending mentions still inside the inbox window.
4. A second, structurally different harness passes criterion 1 by
   template (or preset) change alone — the engine byte-identical.
5. The core CLI dispatches `soulstream wrap` to `soulstream-wrap` with
   the resolved identity in the child's environment, and an unknown verb
   without a matching binary still fails with the CLI's own usage error.
